## Phase 2 — Phone/OTP auth: backend (done)

Per §3.1, mirroring the structure of Medusa's own `auth-emailpass` reference provider:

- **`phone-otp-auth` module** (`AbstractAuthModuleProvider`): `authenticate()` (request OTP), `validateCallback()` (verify OTP, creates the auth identity on first successful verification — passwordless auth has no separate signup screen), `register()` (delegates to `authenticate()` — the framework expects it implemented, but nothing in this flow's real UX calls it separately). Registered in `medusa-config.ts` under the Auth module's `providers`, alongside `auth-emailpass` (both work side by side).
- **`msg91-notification` module** (`AbstractNotificationProviderService`, channel `sms`): the only place MSG91's API is called from. **No MSG91 account was available to build against** (see the session's earlier decision) — when `MSG91_AUTH_KEY`/`MSG91_FLOW_ID` aren't set, it logs the OTP to the backend console instead of sending, so the full flow is testable without a real account. The real MSG91 call (Flow API) is implemented but **unverified against a live account** — flagged in its own code comment, since the exact template-variable key names are account/template-specific and may need adjusting once real credentials exist.
- **`send-otp` subscriber**: listens for `phone-auth.otp.generated`, resolves the Notification Module, calls `createNotifications()`. Decouples auth logic from notification delivery — a slow/down SMS provider can't block or fail the auth request itself (`authenticate()` catches and logs an emit failure rather than throwing).
- **Redis-backed hardening** (`src/lib/redis.ts`, a shared client): resend cooldown (60s), per-phone hourly rate limit (5/hr), max verification attempts (5, then the OTP is invalidated outright even if the correct code is later submitted), single-use OTP (cleared on successful verify). Per-IP rate limiting via `src/api/middlewares.ts` (20/hr, looser than the per-phone limit since one IP can represent several legitimate customers behind NAT).
- **Phone normalization** to E.164 via `libphonenumber-js` (default region `IN`) in both `authenticate()` and `validateCallback()` — so `9876543210` and `+919876543210` resolve to the same account.

**A real bug caught only by live testing, not type-checking**: the auth module tags each created `provider_identity` row's `provider` field with the provider's *configured* `id` (`medusa-config.ts`), but `this.identifier` inside the provider class reflects its *static* `identifier` property — these silently diverge if you give them different values (which this did: `id: "phone-auth"` for the desired route, `identifier: "phone-otp"` out of habit). Every OTP lookup failed with a generic "No active OTP" until traced back to this. Fixed by aligning the static `identifier` to `"phone-auth"`.

**Verified end-to-end against a live backend** (not just type-checked): full request→console-log→verify→JWT cycle; replay protection (reusing a spent OTP fails); cooldown (immediate re-request fails); phone normalization (requested with `9876543210`, verified with `+919876543210`, matched correctly); 5 wrong attempts → lockout → the *actually correct* OTP also then rejected; per-phone hourly limit (simulated via Redis state); per-IP middleware (real 429 after 20 requests, confirmed via its own Redis counter); `auth-emailpass` still works unaffected alongside the new provider.

**Storefront login UI (done).** `Login` (`modules/account/components/login/`) now has an email/phone tab toggle; the phone tab renders the new `PhoneLogin` component, a two-step form (enter phone → enter OTP). One unified flow for both new and returning customers — matches the backend, which creates the account on first successful verification rather than having a separate signup step.

Two new server actions in `lib/data/customer.ts`, mirroring the existing `login`/`completeLogin` pattern:
- `requestPhoneOtp` calls `sdk.auth.login("customer", "phone-auth", { phone })`.
- `verifyPhoneOtp` — **a real deviation from the architecture doc's stated preference worth calling out**: the doc says to use "the Medusa JS SDK's auth methods, not a bespoke fetch to custom routes," but the SDK's `sdk.auth.callback()` is hardcoded for GET-with-query-params OAuth callbacks (`code`/`state` in the URL) — verified from the SDK's own source, not assumed. Submitting an OTP as a URL query parameter would land it in server logs and browser history, a real security downgrade, so `verifyPhoneOtp` calls `sdk.client.fetch()` directly with a POST body instead. The framework-generated `validateCallback` route itself does accept POST (confirmed live in the backend-only testing above) — only the SDK's specific helper method doesn't fit this shape.
- Getting a **customer-bound** token after creating the customer record doesn't work the same way as email/password's `completeLogin` (which just re-submits the password for an immediate second token) — phone-auth is two-step, so "logging in again" would trigger a whole new OTP round-trip. Uses `sdk.auth.refresh()` instead, the same mechanism the SDK's own OAuth-callback flow uses for this identical "actorless token → bound token" problem.

Verified: type-check and lint clean (one pre-existing `any` cast and three pre-existing `useEffect` warnings, both already tracked, nothing new); the account/login page boots and renders 200 with both tabs present in the SSR output.

**Real bug found only by the user clicking through it in an actual browser, not by anything in this session's own testing:** a brand-new phone signup failed with "Email is required to create a customer." `sdk.store.customer.create()` calls Medusa's built-in customer-account-creation workflow, which has a hardcoded business rule requiring email — even though the Store API's own input schema marks `email` optional (confirmed by reading both the Zod validator *and* the workflow step; only checking the former, which this session did initially, misses this). Discussed with the user: rather than synthesizing a placeholder email (a common but slightly hacky pattern for phone-first signup), the business wants email collected for every customer anyway (shipping/invoicing), so the fix adds a third step to phone signup — **Phone → OTP → Email** — but only for brand-new numbers; a returning customer's OTP verification still logs them in immediately with no extra step. The actorless token from OTP verification is carried forward via a hidden form field into the new `completePhoneSignup` action, which creates the customer with both phone and email, then uses the same `sdk.auth.refresh()` mechanism as before to get a customer-bound token.

**Confirmed working end-to-end by the user in a real browser** — Phone → OTP → Email → logged in, for a brand-new number. This closes the browser-testing gap flagged above; the one thing that actually needed a real browser (the multi-step UI transition) has now been exercised for real, not just verified at the API/SDK level.

## Phase 4 — UPI payment flow & admin verification (done)

Per §2.4/§3.2/§3.4/§4.2 — the manual UPI payment lifecycle, the admin verification pipeline, and the customer-facing status mapping.

## Checkout UX iteration — scheduled delivery, Cash on Delivery, phone sign-in hardening (done)

Outside the original phase numbering, like the UI Redesign pass above — a long iterative session of checkout/account polish, one real new feature (delivery scheduling + COD), and several real bugs caught by live testing and by the user's own manual clicking.

**New feature: delivery date + Cash on Delivery, per §2.4/§2.9.** No new Medusa payment-provider module — `cart.metadata.payment_method: "upi" | "cod"` and `cart.metadata.requested_delivery_date: "YYYY-MM-DD"`, same bespoke-metadata convention already established for the UPI "I've Paid" flag. `completeCartWorkflow` doesn't care how a payment session got authorized, so `Review`'s place-order logic stays payment-method-agnostic; the only behavioral split is which UI renders and how `getCustomerOrderStatus` (§2.7) treats the order afterward.
- **Storefront**: a single `<input type="date">` (no ASAP/Scheduled radio — deliberately simplified to one field, defaulting to today, after discussing the drop-off risk of an extra decision) inside the address step, just above "Continue to review"; a separate "Payment method" card (UPI/COD) that only appears once the address step is *not* open, so there's never two calls-to-action on screen at once (the same rule was then applied to "Place order" itself, which had been showing in the sidebar regardless of step).
- **Backend validation**: `completeCartWorkflow.hooks.validate` rejects a past delivery date — found the hard way that **Medusa allows only one `validate` handler per workflow**; the new date-check hook crashed the backend on startup ("Cannot define multiple hook handlers") by sitting next to the existing minimum-order-value hook. Fixed by merging both checks into one handler in `validate-minimum-order-value.ts`. "Today" is computed via an explicit `Asia/Kolkata`-anchored `Intl.DateTimeFormat`, not ambient server time — a naive compare would misjudge the cutoff for ~5.5 hours after each UTC midnight if the backend process isn't actually running in IST.
- **Status mapping (§2.7)**: `getCustomerOrderStatus` takes an optional `paymentMethod` — for `"cod"` it short-circuits straight to "Order Confirmed" (after the existing cancellation/fulfillment checks, so those still take priority), skipping the whole payment-verification branch entirely, since COD has no pre-payment step. `isAwaitingPayment()` needed no change — it's a pure function of the resulting label, so the UPI QR naturally stops rendering for COD orders with zero other template changes.
- **Admin**: the existing payment-verification widget branches its copy on `order.metadata.payment_method === "cod"` ("Cash on Delivery" / "Mark Cash Collected" instead of "UPI Payment Verification" / "Mark Payment Verified") but reuses the exact same `verify-order-payment` workflow and route — capturing an authorized payment is mechanically identical whether the admin is confirming a UPI transfer or confirming cash was physically collected. A new, separate, read-only `order-delivery-schedule.tsx` widget shows the requested delivery date — kept as its own widget rather than folded into the payment one, matching the existing one-widget-per-concern pattern.
- **A real pre-existing bug found and fixed along the way, unrelated to this feature but surfaced by testing it**: `CheckoutForm` was calling a cache-revalidating helper (`ensureDefaultShippingMethod`) directly during server-component render, to self-heal a cart that has an address but no shipping method. Next.js 15 disallows calling `revalidateTag` during render ("used revalidateTag ... during render which is unsupported") — this crashed the checkout page outright for any cart in that state. Fixed by moving the self-heal into a small client component that runs it in a `useEffect` after mount instead.
- **Full manual test pass, with the user's explicit one-time permission to drive Playwright MCP for it** (standing instruction is otherwise no MCP UI testing unless told): all 2×2×2 corners of {new account, old/returning account} × {ASAP, scheduled date} × {UPI, COD} exercised live, plus a forced past-date submission (bypassing the client-side guard directly via the backend API) to confirm the server-side hook actually rejects it, not just the UI. One cosmetic issue flagged, not yet fixed: the rejected-date error reads "Error setting up the request: ..." — a generic wrapper prefix from the shared `medusaError` util that makes an otherwise-clear validation message sound like a network glitch.

**Checkout summary/cart redesign** (several rounds of layout feedback): removed the old standalone "Review" step/card entirely — "Place order" and a one-line terms sentence moved into the bottom of the "In your Cart" summary card, matching the common Amazon/Shopify pattern of anchoring the final CTA to the order summary rather than a separate step. The summary card is capped to the viewport height, with only the items list as the scrollable region, so the button stays visible without scrolling regardless of cart size or screen height — the first attempt at this used the item list's own `overflow-y-auto`, which didn't actually size correctly inside the flex layout (the scroll container needs to be the actual flex-sized element, not a non-flex grandchild of it); fixed by moving the scroll styling to the right element. Cart quantity UI (`ShopCard`, cart line items) got a `−`/editable-number/`+` stepper (already built), plus: the auto-opening cart-preview dropdown on every add-to-cart was removed per explicit feedback (the nav badge count updating is enough feedback); a real bug in the dropdown's thumbnail (`item.variant.product.images`, which is never populated — the image-fallback fix actually attaches images to `item.product.images`) was found and fixed, matching bugs already fixed elsewhere for the same root cause; `ShopCard` now initializes from any existing cart line for that product, so a product already in the cart shows the stepper immediately instead of a bare "Add to Cart" after navigating away and back.

**Checkout address prefill for returning customers**: the shipping-address form now prefills name/email/phone from the signed-in customer's own record (and pre-selects their default saved address in the dropdown) when the cart has no address yet, instead of showing a blank form to someone who's already signed in. Two real bugs found while building this, both only visible through actual browser testing, not type-checking:
- A prefill-sync effect treated `cart.shipping_address` being a non-null *object* as "the cart already has a real address," unconditionally overwriting the form with it — but Medusa creates a **blank stub address** (every field empty string, not null) automatically when a cart's region/country gets set, well before the customer ever types anything. The blank stub was winning over the customer-based prefill. Fixed by checking for actual content (`shipping_address?.address_1`) instead of mere truthiness.
- A customer who signs in on the address step **without navigating away** never got prefilled at all — the component wasn't remounting, so React's `useState` initial value (computed back when `customer` was still `null`) was never revisited. Fixed with a dedicated effect that reacts to `customer` arriving later.

**Security: cart-cookie lifetime.** Found that a cart's ID cookie (`_medusa_cart_id`) persisted for 7 days regardless of auth state, and Medusa treats "knowing the cart ID" as sufficient to read a cart's full contents — including a previously-saved shipping address (name/phone/street) — with no auth check. On a shared/returned-to browser, this left a multi-day window where someone could see PII from a session that *was* authenticated at the time but no longer is. Confirmed live against the actual DB (a lingering cart still had `customer_id` and a full address attached days later). Couldn't reliably distinguish "stale cart from days ago" from "guest who just typed a known email mid-checkout" server-side (Medusa auto-links a cart to an existing customer by email match with zero auth, by design) — so the fix shrinks the exposure window itself instead: cart-cookie lifetime cut from 7 days to 1 day, still covering same-day shopping across tab closes. (`signout()` already correctly cleared both the auth and cart cookies together on explicit logout — that part needed no change.)

**Sign In: check the phone number exists before sending an OTP.** Previously, Sign In sent an OTP to *any* number, including ones with no account, only discovering "no account" after the customer entered a correct code — confusing, and makes them verify a code for nothing. New backend route `GET /store/customers/phone-exists`, rate-limited by the same per-IP limiter as the OTP endpoint; Sign In's `PhoneLogin` instance checks it first and shows "we couldn't find an account" immediately, before ever sending an OTP. **Deliberately scoped to the dedicated Sign In page only** — checkout's own phone step still lets a brand-new number sign up inline (the point of that flow), so it never sets this flag.
- **A real data-consistency bug found while building this**: `customer.phone` was stored inconsistently across existing accounts — some as E.164 (`+91XXXXXXXXXX`), some as a bare 10-digit string — depending on which code path first wrote it (signup vs. profile edit never normalized the raw typed value). The new exists-check, which normalizes to E.164 before comparing, would have silently failed to find any customer stored in the bare format. Fixed two ways: a new shared `normalizeIndianPhone()` util (libphonenumber-js, region `IN`) is now called on every write to `customer.phone` (signup, profile edit) going forward; and the exists-check route itself matches *both* historical formats, so existing accounts work without needing a data migration.
- Every phone input in the app (Sign In, Create Account, Profile, and all five address forms — checkout shipping/billing and the three account-address forms) now restricts to digits-only, max 10 characters, with a numeric keyboard on mobile — consistent with the India-only, `+91`-by-default scope.

**UI polish, this pass**: order-confirmation page — the order-info block redesigned from plain stacked text into a bordered card with a colored status badge (new shared `STATUS_BADGE_COLOR` map, moved out of the account order-card component so both places use the same colors) and a highlighted Cash-on-Delivery note; went through two further rounds of layout feedback (a responsive grid that turned out to overlap text on narrow/mixed-width content, then simplified to a single vertical list — "Order number," "Order date," "Delivery date," "Confirmation sent to," in that order — since a stacked list doesn't have the column-width problem a grid does for variable-length content like an email address); clear section dividers added between the order-info, Summary, and Delivery blocks, which had no visual separation before. "Company" renamed to "Landmark" across all five address forms — kept wired to Medusa's native `company` field under the hood (no schema change), since this business only needs a local landmark for delivery, not a company name. UPI QR centering made more robust (explicit `flex flex-col items-center` instead of relying on inherited `text-align: center`, which doesn't reliably center a raw `<img>` in every browser).

**Recurring dev-server instability, same root cause flagged in Phase 4**: the Turbopack dev server wedged into an unresponsive state multiple times across this session (both the storefront's `.next` build-cache corruption and, separately, a zombie `medusa develop` process from days earlier quietly squatting on port 9000 while a freshly-started one failed to bind) — procedural fix each time (kill stray processes, clear `.next`, restart), not a code issue.

**Not yet done / not yet verified**: the admin widgets' on-screen COD/UPI branching and the "Mark Cash Collected" button weren't clicked through live this session — no admin credentials were available, only verified by reading the code. A cart fully covered by a gift card (`total === 0`) with the Payment Method card hidden was reasoned through but not tested against a real gift card. The rejected-past-date error's "Error setting up the request:" prefix (flagged above) is still there.
