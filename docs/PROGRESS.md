**Catalog seed**: real business data (product catalog + Davangere pincode list) supplied directly, with a few gaps filled in deliberately rather than guessed:
- **Pincodes**: 42 unique, deduplicated from the business's list. One pincode (581119, Ranebennur/Haveri district) was dropped — outside the single-district scope this plan assumes.
- **Sand's data shape**: the business wanted "Product: Sand → Variant: M-Sand/P-Sand/Dust → a further wheeler-size choice under that." Medusa doesn't have a third level under a variant — a variant *is* the full combination of a product's options. Modeled as two independent options instead (`Type`: M-Sand/P-Sand/Dust, `Load Size`: 6/8/10-wheeler), so each Type×Load-Size combination becomes its own variant (e.g. "M-Sand / 6-Wheeler Load") — same customer-facing choice, standard Medusa shape.
- **Unpriced placeholders, left for Admin to fill in**: SK Steel, JSW Steel, all 9 Sand variants, all 3 Crushed Stone/Aggregate variants (bulk materials are sold by negotiated truck-load, no fixed rate existed in the source data).
- **Named placeholders** (source data had a rate but no label): "Steel (Standard)" for an unbranded ₹66/kg row; "Size 1"/"Size 2" for the two unlabeled concrete-block prices (₹48/₹52).
- **Tiles**: seeded as an empty category (so it shows in nav) — the source catalog had no tile products at all.
- 15 products, 21 variants total across 6 categories.

**Found and fixed two real bugs during verification** (not just type-checked — actually browsed every category and product page against a live backend):
- Medusa's auto-slugified handle keeps literal `/` and `&` from a product/category name. `/` turns one URL path segment into two (`Aggregates/Jelly` → 404 via a broken nested path); `&` 404s the route outright (`Steel & TMT Bars`, `Bricks & Blocks`, `Clay / Mud Bricks`, `Crushed Stone / Aggregate`). Fixed with an explicit `toHandle()` slugifier applied to every category and product, not just the ones caught in this pass — so a future catalog addition with a `/` or `&` in its name doesn't silently repeat this.
- The core Medusa loader that auto-provisions a default store/sales-channel/publishable-key on first boot (see Phase 0 note above) kept leaving stray rows behind on every reseed, requiring manual SQL cleanup each time. Made the seed script self-cleaning: it now finds and deletes ("Medusa Store"/"Default Sales Channel"/"Default Publishable API Key") before creating its own, revoking the API key first (Medusa refuses to delete an unrevoked key).

Verified end-to-end against a live backend + storefront: all 6 category pages and all 15 product pages return 200; a real price (₹330, Ultratech Cement) resolves through the pricing pipeline for the seeded region; the pincode check returns `true` for a serviceable pincode and `false` for the dropped one (581119).

## Phase 2 — Phone/OTP auth: backend (done)

Per §3.1, mirroring the structure of Medusa's own `auth-emailpass` reference provider:

- **`phone-otp-auth` module** (`AbstractAuthModuleProvider`): `authenticate()` (request OTP), `validateCallback()` (verify OTP, creates the auth identity on first successful verification — passwordless auth has no separate signup screen), `register()` (delegates to `authenticate()` — the framework expects it implemented, but nothing in this flow's real UX calls it separately). Registered in `medusa-config.ts` under the Auth module's `providers`, alongside `auth-emailpass` (both work side by side).
- **`msg91-notification` module** (`AbstractNotificationProviderService`, channel `sms`): the only place MSG91's API is called from. **No MSG91 account was available to build against** (see the session's earlier decision) — when `MSG91_AUTH_KEY`/`MSG91_FLOW_ID` aren't set, it logs the OTP to the backend console instead of sending, so the full flow is testable without a real account. The real MSG91 call (Flow API) is implemented but **unverified against a live account** — flagged in its own code comment, since the exact template-variable key names are account/template-specific and may need adjusting once real credentials exist.
- **`send-otp` subscriber**: listens for `phone-auth.otp.generated`, resolves the Notification Module, calls `createNotifications()`. Decouples auth logic from notification delivery — a slow/down SMS provider can't block or fail the auth request itself (`authenticate()` catches and logs an emit failure rather than throwing).
- **Redis-backed hardening** (`src/lib/redis.ts`, a shared client): resend cooldown (60s), per-phone hourly rate limit (5/hr), max verification attempts (5, then the OTP is invalidated outright even if the correct code is later submitted), single-use OTP (cleared on successful verify). Per-IP rate limiting via `src/api/middlewares.ts` (20/hr, looser than the per-phone limit since one IP can represent several legitimate customers behind NAT).
- **Phone normalization** to E.164 via `libphonenumber-js` (default region `IN`) in both `authenticate()` and `validateCallback()` — so `9876543210` and `+919876543210` resolve to the same account.

**A real bug caught only by live testing, not type-checking**: the auth module tags each created `provider_identity` row's `provider` field with the provider's *configured* `id` (`medusa-config.ts`), but `this.identifier` inside the provider class reflects its *static* `identifier` property — these silently diverge if you give them different values (which this did: `id: "phone-auth"` for the desired route, `identifier: "phone-otp"` out of habit). Every OTP lookup failed with a generic "No active OTP" until traced back to this. Fixed by aligning the static `identifier` to `"phone-auth"`.

**Verified end-to-end against a live backend** (not just type-checked): full request→console-log→verify→JWT cycle; replay protection (reusing a spent OTP fails); cooldown (immediate re-request fails); phone normalization (requested with `9876543210`, verified with `+919876543210`, matched correctly); 5 wrong attempts → lockout → the *actually correct* OTP also then rejected; per-phone hourly limit (simulated via Redis state); per-IP middleware (real 429 after 20 requests, confirmed via its own Redis counter); `auth-emailpass` still works unaffected alongside the new provider.

**Storefront login UI (done).** `Login` (`modules/account/components/login/`) now has an email/phone tab toggle; the phone tab renders the new `PhoneLogin` component, a two-step form (enter phone → enter OTP). One unified flow for both new and returning customers — matches the backend, which creates the account on first successful verification rather than having a separate signup step.

Two new server actions in `lib/data/customer.ts`, mirroring the existing `login`/`completeLogin` pattern:
- `requestPhoneOtp` calls `sdk.auth.login("customer", "phone-auth", { phone })`.
- `verifyPhoneOtp` — **a real deviation from the architecture doc's stated preference worth calling out**: the doc says to use "the Medusa JS SDK's auth methods, not a bespoke fetch to custom routes," but the SDK's `sdk.auth.callback()` is hardcoded for GET-with-query-params OAuth callbacks (`code`/`state` in the URL) — verified from the SDK's own source, not assumed. Submitting an OTP as a URL query parameter would land it in server logs and browser history, a real security downgrade, so `verifyPhoneOtp` calls `sdk.client.fetch()` directly with a POST body instead. The framework-generated `validateCallback` route itself does accept POST (confirmed live in the backend-only testing above) — only the SDK's specific helper method doesn't fit this shape.
- Getting a **customer-bound** token after creating the customer record doesn't work the same way as email/password's `completeLogin` (which just re-submits the password for an immediate second token) — phone-auth is two-step, so "logging in again" would trigger a whole new OTP round-trip. Uses `sdk.auth.refresh()` instead, the same mechanism the SDK's own OAuth-callback flow uses for this identical "actorless token → bound token" problem.

Verified: type-check and lint clean (one pre-existing `any` cast and three pre-existing `useEffect` warnings, both already tracked, nothing new); the account/login page boots and renders 200 with both tabs present in the SSR output.

**Real bug found only by the user clicking through it in an actual browser, not by anything in this session's own testing:** a brand-new phone signup failed with "Email is required to create a customer." `sdk.store.customer.create()` calls Medusa's built-in customer-account-creation workflow, which has a hardcoded business rule requiring email — even though the Store API's own input schema marks `email` optional (confirmed by reading both the Zod validator *and* the workflow step; only checking the former, which this session did initially, misses this). Discussed with the user: rather than synthesizing a placeholder email (a common but slightly hacky pattern for phone-first signup), the business wants email collected for every customer anyway (shipping/invoicing), so the fix adds a third step to phone signup — **Phone → OTP → Email** — but only for brand-new numbers; a returning customer's OTP verification still logs them in immediately with no extra step. The actorless token from OTP verification is carried forward via a hidden form field into the new `completePhoneSignup` action, which creates the customer with both phone and email, then uses the same `sdk.auth.refresh()` mechanism as before to get a customer-bound token.

**Confirmed working end-to-end by the user in a real browser** — Phone → OTP → Email → logged in, for a brand-new number. This closes the browser-testing gap flagged above; the one thing that actually needed a real browser (the multi-step UI transition) has now been exercised for real, not just verified at the API/SDK level.

The pincode-check side of this phase was already done in Phase 1 (§2.3/§3.3/§4.2 — the `delivery-area` module and the checkout address-step gate). The only remaining piece was minimum-order-value enforcement (§2.5).

- **Server-side (authoritative)**: `apps/backend/src/workflows/hooks/validate-minimum-order-value.ts` consumes `completeCartWorkflow`'s `validate` hook — the framework's own extension point for exactly this ("executed before the order is created and the payment is authorized... throw an error to stop the workflow execution"). This file has no exports; it's picked up purely for the side effect of registering the hook, via the same generic file-auto-import mechanism that loads every file under `src/workflows/` (confirmed by reading Medusa's `ResourceLoader` source, not assumed).
- **Client-side (fast UX feedback only)**: the `Review` checkout step shows a "minimum order of ₹X, add ₹Y more" message and withholds the "Place order" button when under threshold — but this is pure UX sugar; the hook above is what actually decides.
- **Threshold**: a single env var each side (`MIN_ORDER_VALUE_INR` backend, `NEXT_PUBLIC_MIN_ORDER_VALUE_INR` storefront — duplicated across two apps rather than one shared source, an accepted tradeoff per §2.5's own "single scalar that changes rarely, escalate to DB-backed only if needed" framing). **Per the user's choice, left unset (disabled, no minimum) in both** — the mechanism is fully wired and tested, just not actively enforcing a real number yet. Set both to the same value whenever the business decides on one.
