# Construction Materials E-Commerce Platform — Architecture & v1 Plan

## Context

We're launching an e-commerce platform for construction materials (cement, steel, sand, aggregates, bricks, tiles) in a single district in Karnataka. The business already runs deliveries manually (no delivery integration needed) and collects payment via UPI outside any gateway. The goal of this document is to lock in a concrete architecture and build sequence for a v1 that is deliberately simple but production-quality — no speculative multi-district, multi-payment-gateway, or notification infrastructure.

The working directory (`/Users/sannidihim/construction-hub`, git repo `construction-hub` on GitHub) already contains a **Medusa DTC Starter** scaffold: a Turborepo monorepo with `apps/backend` (Medusa v2) and `apps/storefront` (Next.js 15.5/React 19). Investigation found:
- `apps/backend` is essentially a **blank Medusa v2 skeleton** — `medusa-config.ts` only has `projectConfig` (no modules registered at all), no Stripe/DTC-specific dependencies, and `src/modules`/`workflows`/`subscribers`/`jobs` are empty placeholders. The only real artifact is `src/migration-scripts/initial-data-seed.ts`, which seeds generic Medusa demo apparel data (Shirts/Sweatshirts, a Denmark/EUR region) — irrelevant and to be replaced.
- `apps/storefront` has a **substantial, working DTC funnel**: `[countryCode]`-based routing, product browsing (PDP/store/categories), cart, a Stripe-based checkout, and a full account module (login, addresses, orders, profile). This is real, reusable plumbing.

**Decision: reuse + strip down**, not a fresh build. The backend costs the same either way (near-empty). The storefront's browse/cart/account plumbing is expensive to rebuild from scratch and only needs its Stripe payment step and multi-region/locale layer removed — bounded, mechanical work, much cheaper than reconstructing PDP/cart/account UX from zero.

All product/business decisions below were confirmed directly with the user; this plan does not assume anything beyond them.

## Confirmed Decisions

- **Units**: Fixed-pack variants, integer quantity (e.g. "Cement 50kg bag", "Bricks bundle of 500") — maps directly onto Medusa's native product/variant/option model. No custom unit-of-measure or decimal-quantity logic.
- **Auth**: Both email/password (Medusa's stock `auth-emailpass` provider) and phone + OTP (custom auth provider, SMS via **MSG91**).
- **Payment**: Static UPI QR (business's own fixed UPI ID), no payment gateway/aggregator. Verification is **pure manual, no proof captured** on the order — admin checks their own bank/UPI app and marks orders verified in Medusa Admin. **Cash on Delivery added post-launch-prep** as a second method, chosen at checkout alongside UPI — represented purely via `cart`/`order.metadata.payment_method`, not a second Medusa payment-provider module (see §2.4).
- **Payment-state modeling**: Medusa's **built-in System payment provider** (`pp_system`), not a custom provider module. Medusa documents this provider explicitly as a cash-on-delivery-style placeholder — no gateway call, merchant manages the payment lifecycle themselves — which matches the UPI-QR case directly. The order is created while the payment session sits in Medusa's `pending_authorization` state (a state Medusa designs for exactly this: bank transfers, vouchers, pay-later methods), and later transitions to `authorized`/`captured` once the admin confirms. This still keeps payment history inside Medusa's native ledger, without writing a custom `IPaymentProvider` implementation. See §2.4.
- **Delivery area check**: Pincode allowlist for the single target district, checked at the address step.
- **Minimum order value**: enforced (no delivery fee otherwise).
- **Notifications**: none for v1 — customers check status by logging in.
- **Cancellation**: admin-only, via stock Medusa Admin order cancel; no in-app refund automation (refunds happen manually, off-platform).
- **Daily price updates**: via the standard Medusa Admin UI, one variant at a time — no bulk tooling for v1.
- **Fulfillment/delivery**: Medusa's **built-in manual fulfillment provider** (`@medusajs/fulfillment-manual`) — no custom delivery module. One shipping option ("Business Delivery," ₹0, since there's no delivery fee) bound to it. Admin progresses an order through Medusa's native fulfillment lifecycle (Create Fulfillment → Mark as Shipped → Mark as Delivered) exactly as designed; "Mark as Shipped" is the "Out for Delivery" step, "Mark as Delivered" is the final step. See §2.6.
- **GST/tax**: not finalized — **default to tax-inclusive flat pricing** for v1 (no separate Tax module configuration), revisit before launch if the business needs a shown tax line.
- **Deployment**: **Medusa Cloud for both backend and storefront**, using Cloud's "Storefronts on Cloud" feature, which requires (and this repo already has) a Turbo/Nx monorepo layout — single platform, no separate Vercel account needed.
- **SMS/OTP provider**: MSG91.

## 2. Data Model

### 2.1 Categories & catalog
Use Medusa's native `ProductCategory` — flat taxonomy: Cement, Steel & TMT Bars, Sand, Aggregates/Jelly, Bricks & Blocks, Tiles. One INR region for the target Karnataka district (no multi-country tax complexity), one stock location representing the business's yard.

**Search**: Medusa's built-in Store API search (`POST /store/products/search` with a `q` keyword param, backed by Postgres) is sufficient for v1's catalog size (a few dozen–hundred SKUs across six categories). No Algolia/MeiliSearch integration for v1 — that's real infrastructure and cost for a search problem this catalog doesn't have yet; revisit only if the catalog grows enough that keyword relevance becomes a real complaint.

**Product images**: Medusa Cloud's storefront hosting currently does not support Next.js's built-in Image Optimization (`next/image`'s automatic resizing/format conversion doesn't run there). Two options, decided in Phase 0: disable Next.js image optimization (`images.unoptimized: true` in `next.config.js`) and serve pre-sized images, or point `next.config.js`'s image loader at an external optimizer/CDN. Given v1's small, admin-curated catalog (not user-generated uploads), the simplest fix — upload reasonably-sized images and disable optimization — is recommended over adding a third-party image service for v1; revisit if product photos start being large/unoptimized uploads at scale.

### 2.2 Fixed-pack variants
No new model needed. Product = the material; Product Option = "Pack Size"; Variant = the sellable SKU with its own price/inventory (e.g. "TMT Steel 12mm x 12ft"). Even single-pack-size materials get a 1-value option, to keep the PDP option→variant selection code path (`apps/storefront/src/modules/products/components/product-actions/`) uniform. Customer quantity = Medusa's existing `LineItem.quantity`.

### 2.3 Pincode delivery-area allowlist
New custom module `apps/backend/src/modules/delivery-area/`:
- Model: `ServiceablePincode { id, pincode (unique, indexed), area_label?, is_active }`.
- Service: `isServiceable(pincode)` + standard CRUD.
- Rationale for a DB-backed module over a config/env list: admin needs to add/remove pincodes without a backend redeploy.
- Migration via `medusa db:generate delivery-area`; seeded via the new seed script (Phase 1).

### 2.4 Payment-state (order created before payment is confirmed)

**No custom payment-provider module.** Use Medusa's built-in System payment provider (`pp_system`), registered as the sole provider for the region's payment module. It performs no gateway call; Medusa documents it as a cash-on-delivery-style placeholder where the merchant manages the payment lifecycle out of band — exactly the UPI-QR case.

Checkout sequence (matches the flow below, and directly addresses the "customer pays, order never gets created" gap):

```
Cart → Address + pincode validation → Shipping method
  → completeCartWorkflow runs: ORDER IS CREATED, payment session = pending_authorization
  → Storefront shows UPI QR, referencing the just-created order/payment id
  → Customer pays off-platform
  → Admin verifies (bank/UPI app) and captures the payment in Admin
  → Payment session = authorized → captured; order.payment_status updates automatically
  → Order can be fulfilled — see §2.6 for what happens from here through delivery
```

Because the order exists the moment checkout completes (before any money has changed hands), there is no window where a successful payment can arrive with no order to reconcile it against — the order is already sitting in Medusa in a "payment pending" state, and the admin's job is only ever to *advance* an existing order, never to reconstruct one.

This keeps payment history inside Medusa's standard payment/capture ledger with zero custom provider code. If proof capture or real refund tracking is needed later, a custom provider can still be introduced then — nothing here forecloses that.

**Mobile vs. desktop presentation**: a static QR alone is a broken experience for a customer checking out on the same phone they'd need to scan it with — there's no camera-to-screen loop on one device. The standard fix (and the one used here): the payment string is a single UPI intent URI (`upi://pay?pa=<vpa>&pn=<name>&am=<order total>&cu=INR&tn=<order id>`); on mobile, render it as a tappable "Pay via UPI app" button (opens the customer's UPI app directly with the amount prefilled), and on desktop, render the same string as a QR code image for the customer to scan with their phone. One generated string, two presentations, chosen by a simple device check — no separate logic per platform.

**Cash on Delivery (added later, same `pp_system` mechanics)**: the customer picks UPI or COD in a "Payment method" step before placing the order. This choice is stored as `cart.metadata.payment_method: "upi" | "cod"` (absent = UPI, so every pre-existing cart is unaffected) — deliberately **not** a second Medusa payment-provider module, since `completeCartWorkflow` doesn't care how a payment session got authorized; it only needs *some* registered provider to produce one, which `pp_system` already does for free regardless of method. The flagged tradeoff: `payment_method` lives in an untyped/unindexed JSON column, which is fine at today's volume but is the seam where a real `provider_id`-based split would eventually be cleaner if COD volume grows enough to need dedicated financial reporting. Checkout-side logic (initiating the payment session, calling `completeCartWorkflow`) is identical regardless of method — only the UI (QR vs. "Order Placed") and the customer-facing status (§2.7) branch on it. The admin side reuses the exact same "Mark Payment Verified" capture action (§3.2) for both — collecting cash and confirming a UPI transfer both end in the same "capture this order's authorized payment" step; only the widget's copy changes ("Mark Cash Collected").

### 2.5 Minimum order value
Enforced **server-side**, not just client-side (so it can't be bypassed via direct Store API calls):
- Store the threshold as an env var (`MIN_ORDER_VALUE_INR`) — a single scalar that changes rarely; escalate to a DB-backed setting only if the business wants to self-serve changes without a deploy.
- Enforce via a workflow step composed into cart completion, rejecting with a clear error if the cart total is under threshold.
- Also enforce client-side in the storefront checkout step for fast UX feedback (belt and suspenders).

### 2.6 Fulfillment & delivery (Medusa's built-in fulfillment system, no custom delivery module)

The original flow ("business delivers manually, admin marks Delivered") still needs to run through Medusa's actual fulfillment machinery rather than jumping straight from payment to a bare "Delivered" flag — otherwise there's no modeled state for "packed but not yet out," no audit trail, and no natural place to hang a future tracking/notification feature. Medusa already has exactly this lifecycle built in:

```
Stock Location (the business's yard — already defined in §2.1)
      ↓
Shipping Profile ("Default") + Shipping Option ("Business Delivery", ₹0, single region)
      ↓
Manual Fulfillment Provider (@medusajs/fulfillment-manual, built-in — no custom code)
      ↓
Admin: Create Fulfillment  →  Mark as Shipped ("Out for Delivery")  →  Mark as Delivered
```

Configuration (Phase 0/1, not custom code):
- Register the manual fulfillment provider for the fulfillment module in `medusa-config.ts` (same pattern as the payment module in §2.4).
- Create one `ShippingProfile` and one `ShippingOption` ("Business Delivery") scoped to the single region, priced at ₹0 (no delivery fee, per the confirmed decision), associated with the stock location from §2.1.
- No shipping-rate calculation, carrier integration, or tracking-number requirement — `add tracking number` is optional in Medusa's UI and is skipped for v1.

Admin usage (no new UI needed — this is stock Medusa Admin):
1. Once payment is verified (§2.4), admin clicks **Create Fulfillment** on the order — status becomes `fulfilled`.
2. When the business actually dispatches the order, admin clicks **Mark as Shipped** — sets `shipped_at`. This is the "Out for Delivery" state.
3. Once delivered, admin clicks **Mark as Delivered** — sets `delivered_at`. This is the terminal success state.
4. A fulfillment can only be cancelled before it's shipped or delivered (Medusa enforces this) — matches the confirmed admin-only cancellation decision; no custom guard needed here, unlike the payment-side cancellation interaction flagged in §3.2.

### 2.7 Customer-facing status mapping

Medusa tracks payment state (`payment_status`) and fulfillment state (`fulfillment_status`) as two separate fields, plus an overall `order.status` (e.g. `canceled`). Customers shouldn't see Medusa's internal vocabulary directly — a small **derived mapping**, not a new stored field, translates the pair (plus the customer's own "I've Paid" self-report, §4.2) into one of seven labels:

| Customer sees                | Derived from                                                                        |
|-------------------------------|--------------------------------------------------------------------------------------|
| Payment Pending               | `payment_status = pending_authorization`, no customer self-report yet                |
| Payment Verification Pending  | `payment_status = pending_authorization`, `metadata.payment_customer_confirmed = true` (customer clicked "I've Paid") — still just a hint, not a capture |
| Order Confirmed               | `payment_status = authorized` or `captured`, `fulfillment_status = not_fulfilled`    |
| Order Processing              | `fulfillment_status = fulfilled` (fulfillment created, not yet shipped)              |
| Out for Delivery              | `fulfillment_status = shipped`                                                       |
| Delivered                     | `fulfillment_status = delivered`                                                     |
| Cancelled                     | `order.status = canceled` (overrides all of the above)                               |

This mapping is pure, stateless, and lives as a small shared utility (e.g. `apps/storefront/src/lib/util/order-status.ts`), consumed by the order-status storefront pages (§4.2) and mirrored in the admin order widget (§3.4) so admin and customer never see contradictory labels for the same order.

**Cash on Delivery (§2.4) bypasses the payment-pending branch entirely**: given `order.metadata.payment_method === "cod"`, the mapping short-circuits straight to "Order Confirmed" immediately after the `fulfillment_status`/cancellation checks (which still take priority, same as for UPI) — there's no pre-payment verification step for COD, since cash is collected physically at delivery. Important nuance: for a COD order, "Order Confirmed" means *placed*, not *paid* — actual payment-captured state still lives on the order's real payment record, and only advances when admin clicks "Mark Cash Collected" (§3.2/§3.4). Nothing downstream should read this label as proof money has moved.

### 2.8 Checkout-time robustness (stock, pricing, duplicate submission)

Stock availability at completion, price changes between cart creation and checkout, and duplicate checkout submissions are real risks, but they belong to cart/order **creation**, not payment verification (§3.2) — by the time verify-payment runs, the order already exists with a locked-in total:
- **Stock becoming unavailable during checkout**: Medusa's cart-completion workflow includes its own inventory-availability/reservation checks as a core step; this is expected to be handled natively, not by custom code — verify with an explicit test in Phase 1 (reduce a variant's stock to zero mid-checkout, confirm completion fails cleanly) rather than assuming.
- **Inventory concurrency**: two customers completing checkout for the last unit of the same variant at the same time should not both succeed. This is a distinct case from the above (that's an admin zeroing stock; this is a race between two simultaneous buyers) — Medusa's inventory reservation is expected to serialize this at the database level, but it must be tested explicitly with a genuine concurrent request (e.g. two parallel `completeCartWorkflow` calls in a test script), not just sequential manual clicks which would never actually race.
- **Price changing after cart creation**: Medusa computes cart totals dynamically up until the order is created; the order line items snapshot the price only at `completeCartWorkflow`. This is why §2.4 already has the UPI QR read the amount from the just-created order, not a total cached earlier in checkout — confirm with a test that changes a variant's price mid-checkout and checks the QR/admin amount matches the order, not the stale cart view.
- **Duplicate checkout/order submission** (e.g. a double-clicked "place order" button): a completed cart should not be completable a second time. Expected to be native Medusa behavior (a cart is single-use once it transitions to an order) — verify explicitly in Phase 4 rather than assume, and add a storefront-side submit-button disable-while-pending as cheap defense in depth regardless of what the backend guarantees.

### 2.9 Requested delivery date (added later)

Same bespoke-metadata approach as payment method, and for the same reason — no new Medusa fulfillment/shipping-option model needed: `cart.metadata.requested_delivery_date: "YYYY-MM-DD"`, set from a single date field in the address step (defaulting to today; no separate "ASAP vs. Scheduled" choice — simplified to one field after weighing the checkout drop-off risk of an extra decision). Copied onto `order.metadata` automatically the same way `payment_method` is, since `completeCartWorkflow` copies cart metadata onto the new order wholesale. Enforced server-side via the same `completeCartWorkflow.hooks.validate` hook used for the minimum-order-value check (§2.5) — **Medusa allows only one `validate` handler per workflow**, so both checks live in the one hook function, not two separate files. "Today" for the past-date comparison is computed anchored to `Asia/Kolkata` explicitly, not ambient server time, since the backend process's own timezone isn't guaranteed to be IST. Surfaced to admin via a small read-only widget (§3.4); surfaced to the customer alongside "Order date" on the order-confirmation and order-details pages.

### 2.10 Labour & Manpower booking (added later — own module, not an Order)

A labour booking is a lead-capture + status-tracking record, not a sale of inventoried goods — modeling it as a Medusa cart/order (with a virtual "service" product) would pull in machinery (inventory, fulfillment status, a shipping-address model) this doesn't need for what is, operationally, the same "customer submits a request, admin actions it by phone" pattern the business already runs. New standalone module `apps/backend/src/modules/labour-booking/`, mirroring `delivery-area`'s exact scaffold (model + service + index.ts + migration, one workflow per mutation):

- **Model** `LabourBooking`: `service_slug`/`service_name`/`rate_amount` (a snapshot of the chosen static-catalog service at submission time — see below — not a live join, same principle as an order line item snapshotting a product's name/price), `rate_type` (`"day" | "hour"`), `start_date`/`end_date` (day bookings only), `scheduled_time`/`duration_hours` (hour bookings only), `num_workers`, address fields (`address_1`, `landmark`, `city`, `postal_code`, `phone`, `customer_id` nullable, `email` nullable — same loose by-id reference style Medusa itself uses for order↔customer, no hard DB relation), `payment_method` (`"upi" | "cod"`), two independent payment-confirmation booleans, `status` (`"requested" | "confirmed" | "completed" | "cancelled"`), `admin_note`.
- **Two separate payment-confirmation fields, not one** — `payment_customer_confirmed` (the customer's own "I've Paid" self-report, a hint) and `payment_received` (the admin's actual confirmation) — mirroring how Materials orders already keep the customer's self-report and the real payment-capture state as two distinct signals, not one conflated boolean. An estimated total (for the UPI QR amount and the confirmation page) is computed as `rate_amount × (day: date-range length | hour: duration) × num_workers`, not stored — there's no fixed-price contract, admin can adjust by phone.
- **Service catalog stays in the static `lib/data/labour-services.ts` file** for v1 — no "manage labour services" admin CRUD yet, matching the placeholder-data convention already used for both Labour and Engineering before this. A booking snapshots the service's name/slug/rate at submission, so a later catalog rate change doesn't retroactively alter an old booking's record.
- **Lead-time cutoffs, enforced server-side** (not just a disabled UI option) in `create-labour-booking.ts`'s workflow: a day booking whose start date is *today* must be submitted before 8:30 AM IST (at/after, today is no longer selectable — earliest becomes tomorrow); an hour booking's start time must be at least 1 hour after the moment of submission, with no separate daily cutoff of its own. Both anchored to `Asia/Kolkata`, same reasoning as §2.9's delivery-date check (the backend process's own timezone isn't guaranteed to be IST).
- **Per-hour bookings are restricted to business hours (9:00 AM–5:00 PM)**, enforced both client-side (the storefront's start/end time pickers only offer a 15-minute-step list of selectable times within that window, not a free-form native time input) and server-side (the workflow rejects a requested start/end outside that window, computed as minutes-since-midnight from the stored `scheduled_time`/`duration_hours`).
- **Same serviceable-pincode gate as Materials delivery (§2.3)** — resolves `DeliveryAreaModuleService.isServiceable()` and rejects a booking outside the coverage area, server-side, before the record is created. (This surfaced a pre-existing gap in the Materials checkout flow itself — see the note at the end of §2.3/§3.3: pincode serviceability there had only ever been a storefront UX hint, with nothing stopping a direct Store API call from completing an order outside the area. Fixed at the same time by adding the equivalent check into the existing `completeCartWorkflow.hooks.validate` registration — Medusa allows only one `validate` handler per workflow, so this lives in the same hook function as the minimum-order-value/delivery-date checks, §2.5/§2.9, not a separate file.)
- **Phone verification required before submitting a booking** — reuses the exact same `PhoneLogin` OTP component checkout uses, including its "brand-new phone → email → account created" sub-flow (§3.1); a returning customer's phone/name/saved address prefill the form the same way checkout's address form already does (§3.5/§4.3 below).
- **Status lifecycle is admin-driven only** (`requested → confirmed → completed`, plus `cancelled`), same shape and same "admin advances a request, customer doesn't" model as the order-fulfillment lifecycle (§2.6/§2.7) — just without Medusa's actual fulfillment machinery behind it, since there's no inventory/shipping involved.

### 2.11 Engineering Services quote requests (added later — own module, lead capture only)

"Get a free quote" is a lead the business follows up by phone, not an order, so — like labour bookings (§2.10) — it's its own small module, `apps/backend/src/modules/quote-request/`, mirroring the same scaffold (model + service + index + migration, one workflow per mutation).

- **Model** `QuoteRequest`: `service_slug`/`service_name` (a snapshot of the catalog label, so renaming a service later doesn't rewrite history), `name`, `email`, `phone`, `notes` (nullable, max 1000 chars), `customer_id`, `status` (`new → contacted → quoted → closed`, admin-driven only), `admin_note`. No payment fields — nothing is charged.
- **The stored phone is always the verified one, and is taken server-side.** The route is behind the same phone-OTP gate as labour bookings (`authenticate("customer", "bearer")`), and the create workflow reads `phone` from the authenticated customer's own record rather than the request body — so whatever the client sends or displays, the number on a quote is one that was actually OTP-verified. (Confirmed by trying to spoof `phone`/`service_name` in the body: both ignored.) A customer who signed in by email and has no phone on file is rejected with a clear message rather than stored with a blank/unverified number.
- **Service catalog**: two picklists, one per storefront section — "Engineering Services" (8 services + "Other") and "Other Services" (eight: precast compound walls, steel fabrication, MS/steel gates & grills, UPVC & aluminium doors/windows/partitions — one entry, glass & glazing, waterproofing, roofing, solar water heaters; it was six, with aluminium and UPVC separate, before the supplied photos defined the set). The backend's `service-catalog.ts` is the authoritative list: the workflow rejects any slug not in it and snapshots the name from it, never from the client. The storefront's `lib/data/engineering-services.ts` mirrors it; the two apps can't share a module, so a change means editing both (same accepted tradeoff as `MIN_ORDER_VALUE_INR`). **That duplication is now guarded**: `scripts/check-synced-lists.js`, run as step 4 of `scripts/check.sh`, compares the two copies entry by entry (slug *and* display name) — for these services and for the contact-form subjects (§2.12) — and fails naming exactly what differs. It was added after the names had in fact drifted (the form said "Cost Estimation" and "Complete Turnkey Construction – Foundation to Finishing" while the slider said "Construction Cost Estimation" and "Turnkey Construction & Renovation"); the better-sounding wording was kept everywhere. Slugs are stored identifiers and were left alone; each saved request keeps the name it was submitted with (a snapshot), so a later rename never rewrites history.
- **Validation (server-side, authoritative)**: valid service slug, non-blank name (≤100), well-formed email, notes ≤1000 — each with a clear 400. The storefront mirrors these as inline field errors, but the workflow is the real gate.

### 2.12 Contact messages (added later — own module, open to anyone)

The "Contact Us" page's message form is a lead the business reads and replies to by phone/email, so — like labour bookings (§2.10) and quote requests (§2.11) — it's its own small module, `apps/backend/src/modules/contact-message/` (same scaffold: model + service + index + migration, one workflow per mutation).

- **Model** `ContactMessage`: `topic_slug`/`topic_name` (the "Subject" picklist, snapshotted from a server-side catalog like the quote services), `name`, `email`, `phone` (required), `message`, `customer_id` (nullable), `status` (`new → replied → closed`, admin-driven), `admin_note`.
- **Deliberately not OTP-gated** — unlike quote requests (§2.11) and labour bookings, which require a verified phone. A contact form that demanded sign-in would defeat its purpose, so it's open to anyone; `customer_id` is only set when the sender happened to be signed in (the store route uses `authenticate("customer", "bearer", { allowUnauthenticated: true })`, so a missing *or junk* token is simply treated as a guest). The phone is required and format-validated (parsed with `libphonenumber-js`, region IN, stored as E.164) but, unlike a quote's, **not verified** — the business calls back on whatever was typed.
- **Abuse controls, since there's no sign-in gate**: a per-IP rate limit (5/hour, Redis-backed; the real local Redis persists across backend restarts, so a tripped counter lasts its hour), a honeypot field (a hidden input real visitors never fill — a filled one gets the same `201` success as a real submission but nothing is stored), and the workflow's server-side validation (valid subject slug, non-blank name ≤100, well-formed email, valid phone, message 10–2000 chars).
- **Per-IP limiter refactor**: the existing phone-auth limiter in `middlewares.ts` was hard-wired to OTP requests; it's now a small `createIpRateLimit({ keyPrefix, maxPerHour, message })` factory, with the phone-auth limiter's Redis key and 20/hour ceiling unchanged.

## 3. Custom Backend Work

### 3.1 Phone + OTP auth provider

**Use Medusa's actual Auth Provider lifecycle, not bespoke Store API routes.** Medusa's own reference implementation for exactly this scenario (its "Implement Phone Authentication" tutorial) is a proper `AbstractAuthModuleProvider` with two framework-recognized methods — not two hand-rolled endpoints:

```
Phone Auth Provider (authenticate + validateCallback)
        ↓ emits event on OTP generation
"phone-auth.otp.generated"
        ↓
Subscriber (src/subscribers/send-otp.ts)
        ↓ resolves the Notification Module
Notification Module  →  msg91-notification provider (channel: "sms")  →  MSG91
```

- `apps/backend/src/modules/phone-otp-auth/`, registered in `medusa-config.ts`'s Auth module alongside the stock `auth-emailpass` provider. Implements:
  - `authenticate(input)` — the "request OTP" call. Generates a 6-digit OTP, normalizes the phone number to E.164 first (see below), and returns `{ success: true, location: "otp" }` to signal the callback step is required. Framework auto-generates the route `POST /auth/customer/phone-auth` for this — **no custom route needed**.
  - `validateCallback(input)` — the "verify OTP" call, framework-generated as `POST /auth/customer/phone-auth/callback`. Validates the submitted OTP and, on success, returns the `AuthIdentity`, issuing the same JWT/cookie session Medusa uses everywhere else.
  - `register()` — initial account creation with the normalized phone number as `entity_id`.
- **OTP generation triggers a domain event, not a direct SMS call.** `authenticate()` never talks to MSG91 itself; it emits `phone-auth.otp.generated { phone, otp }` on the event bus. A subscriber resolves `Modules.NOTIFICATION` and calls `notificationModuleService.createNotifications({ to: phone, channel: "sms", template: "otp", data: { otp } })`. This is the decoupling the fix calls for: swapping MSG91 for another provider later means writing a new notification provider, not touching auth logic.
- **MSG91 notification provider**: `apps/backend/src/modules/msg91-notification/`, implementing `AbstractNotificationProviderService` for the `sms` channel, registered under the Notification module's `providers`. This is the only place MSG91's API is called from.
- **OTP storage**: JWT-signed (`jwt.sign({ otp }, jwtSecret, { expiresIn: "5m" })`), stored in the auth identity's `provider_metadata` — no Redis needed just to hold the OTP value itself. Expiry is enforced by JWT verification failing past the TTL. **On successful verification, `provider_metadata.otp` is cleared immediately** so a captured OTP can't be replayed again inside its own TTL window (Medusa's reference tutorial does not do this — it's an explicit hardening addition here).
- **Phone number normalization**: all phone input is normalized to E.164 (e.g. via `libphonenumber-js`) before it's used as `entity_id` or looked up, both in `authenticate()` and `validateCallback()` — otherwise `+919000000000` and `9000000000` would silently become two different accounts (a real gap in Medusa's own tutorial, called out here explicitly).
- **Resend cooldown, max attempts, and rate limiting** — these use Redis, since they need shared, fast-expiring counters that a stateless JWT can't provide on its own:
  - Resend cooldown: reject a new `authenticate()` call for the same phone within N seconds of the last one (Redis key with TTL).
  - Max verification attempts: increment a Redis counter on each failed `validateCallback()`; once a threshold is hit, invalidate the current OTP outright (don't just let it expire) and require a fresh `authenticate()` call.
  - Per-phone rate limiting: cap OTP requests per phone per hour (Redis counter).
  - Per-IP rate limiting: a custom middleware (`apps/backend/src/api/middlewares.ts`, matcher `/auth/customer/phone-auth*`) rejecting excessive request volume from a single IP — this is added at the route-matcher level precisely because Medusa auto-generates the route rather than us owning a custom handler; Medusa's middleware system supports attaching guards to built-in routes this way (its own tutorial does the same thing to guard `/store/customers/me`).
- No delivery-status webhook needed for v1 — fire-and-forget send from the subscriber; OTP verification is check-based, not delivery-confirmation-based.

Note: this SMS usage is unrelated to the "no notifications for v1" decision above — that decision covers *order-status* notifications (email/SMS on order events), which are still explicitly out of scope. OTP delivery is a mechanic of the phone-login feature itself, decided separately, and is the only notification traffic this platform sends in v1.

**Phone-exists check (added later, for Sign In only — §4.2)**: `GET /store/customers/phone-exists?phone=...`, rate-limited by the same per-IP middleware as the OTP routes. Normalizes the phone (same `libphonenumber-js`/`IN` logic) and checks for a matching customer via the query graph, matching against *both* the E.164 and bare-national-number forms — a real inconsistency was found in existing data (`customer.phone` had been written in both formats depending on which code path created it, since neither signup nor profile-edit normalized the raw input before this). Fixed going forward with a shared `normalizeIndianPhone()` util called on every write to `customer.phone`; the exists-check's dual-format match covers accounts written before the fix, without a data migration. Worth flagging: this endpoint necessarily lets anyone check whether a given phone number has an account here (that's the point), which is a mild enumeration surface — accepted for this business, mitigated only by the same rate limit as OTP requests.

**Email-conflict check (added later — runs before any OTP)**: `GET /store/customers/email-conflict?email=...&phone=...` answers "would this email stop this phone becoming a new account?". A brand-new phone is turned into an account from the email on the form, and Medusa refuses if another account (`has_account`) already has it — which used to surface only *after* the visitor had requested and entered an OTP. The route reports `conflict: true` only when the email belongs to an account whose phone is **not** the one being verified (phones compared normalized, since `customer.phone` exists in two formats; an account with no phone counts as a conflict, since it still holds the email) — if it's the same phone the OTP just signs them in and nothing is created, so nothing clashes. It has its own per-IP limiter (60/hour; each attempt makes two calls) and is the same mild enumeration surface as phone-exists (anyone can learn an email is registered), accepted on the same terms. It **fails open**: if the check can't be answered the OTP still goes out, because the server's duplicate refusal at account creation remains the real guard.

### 3.2 UPI manual payment verification — a privileged operation, not a generic order update

Cart completes against the built-in `pp_system` provider (2.4); the order exists and its payment session sits in `pending_authorization` with no gateway call ever made. Marking that payment verified moves real money out of "unconfirmed" — it is treated as a privileged operation with its own explicit pipeline, not exposed through Medusa's generic order PATCH:

```
Authenticate admin → Authorize operation → Load order/payment
  → Validate current state → Validate payment amount → Idempotent capture
  → Record verification details
```

- **Authenticate admin** — free, not custom code: any route under `apps/backend/src/api/admin/**` is automatically protected by Medusa's own admin session middleware (this is how Medusa's route convention works — `/admin/*` inherits the same guard as core admin routes, with no opt-in required). This structurally rejects both an unauthenticated request and a customer session (customers and admin users are distinct actor types in Medusa's auth identity model, so a customer's JWT does not satisfy the admin guard) — but it's still an explicit test case (below), not an assumption.
- **Authorize operation** — for v1, "authorized" means "any authenticated admin user." Medusa v2 does have an RBAC system (behind the `MEDUSA_FF_RBAC` feature flag), but it currently has open bugs around permission revocation and sidebar visibility, and the business runs with a small, effectively single-operator admin team per the original requirements — enabling RBAC now would import known-buggy complexity with no real access-control benefit yet. This is a deliberate v1 decision (see Open Items), not an oversight.
- **Load order/payment** — resolve the order and its payment collection by the order id from the route param; a missing/mismatched id fails here, before any state logic runs.
- **Validate current state** — reject if the order is already cancelled (checked explicitly rather than trusted to the payment module alone, given the known upstream cancellation interaction, see Open Items), and reject if the payment is already captured, returning a distinct "already verified" error so the admin UI can tell "first verification" from "duplicate click."
- **Validate payment amount** — reject if the amount being confirmed doesn't equal the order's actual total; no partial/mismatched captures for v1. Catches fat-fingered admin input or a wrong-order mix-up before money is marked received.
- **Idempotent capture** — call Medusa's existing `capturePaymentWorkflow` (or the payment module's `capturePayment`) to perform the actual state transition; Medusa's core capture path already short-circuits once `captured_at` is set, so this step is safe to retry.
- **Record verification details** — `admin_note`/`verified_by`/`verified_at` written to the order once capture succeeds.

Implementation: custom workflow `apps/backend/src/workflows/verify-order-payment.ts` implementing the state/amount checks around Medusa's own capture call, invoked from `apps/backend/src/api/admin/orders/[id]/verify-payment/route.ts` (`POST`) — the "mark payment verified" action surfaced in the admin widget (3.4).

**Explicit test matrix for this endpoint** (Phase 4 exit criteria): unauthenticated request; customer session attempting the route; duplicate verification of an already-captured order; wrong payment amount; already-cancelled order; a payment captured but somehow with no corresponding completed order (regression test that Phase 4's order-before-payment sequencing in §2.4 holds — this should be structurally impossible, prove it stays that way). Cancellation itself (stock Medusa Admin order cancel) must also be tested against an order whose payment is still `pending_authorization` and one whose payment is already `captured` — see Open Items, this interaction has a known upstream rough edge.

- **"My Orders & Requests" — Materials, Labour and Engineering tabs**: the account orders page (renamed from "My Orders" since two of its three tabs are bookings and quote requests, not orders) has three tabs driven by a `?tab=` search param (plain links, not client state — each tab is bookmarkable, only the active tab's data is fetched, and the bare `/account/orders` URL stays Materials so existing links keep working). All three lists use the same compact row (thumbnail/icon · title/sub-line · price or status badge, the whole row being the link — a long history stays scannable instead of one order filling a screen). A booking's detail page, `/account/orders/labour/[id]`, shows the booking info, a **status tracker** (Requested → Confirmed → Completed; a cancelled booking replaces the steps with a single cancelled notice, since cancellation is a terminal exit rather than a stage after "completed"), the UPI QR or COD note, and the address/contact. Status colors, schedule text, estimated total and payment label live in one shared util (`lib/util/labour-booking.ts`) used by the confirmation page, the list rows and the detail page, so a booking never reads differently depending on which page it's on; a cancelled booking is never "awaiting payment", so it no longer shows the UPI QR.
- **Materials delivery tracker**: the Materials order detail page (`order-details-template`) has the same kind of tracker — Order placed → Order confirmed → Processing → Out for delivery → Delivered, with a cancelled notice for cancelled orders — drawn from the *same derived status the badge uses* (§2.7), so the two can't disagree. The two payment-pending statuses (UPI orders waiting on payment) aren't steps of their own: the order exists, so "Order placed" is reached and the next step's hint says what it's waiting for ("Waiting for your payment" / "We're verifying your payment"); COD orders skip straight to confirmed (§2.7), so for them that wait never shows. Verified live across the real orders in the data (UPI and COD; delivered, confirmed, and both payment-pending states). Processing, Out for Delivery and Cancelled had no orders in the dev database to render (order data wasn't mutated to fake them), so they were first covered only by the compiler — the mapping is a `Record` over every non-cancelled status, so a missing status is a compile error — and were then **confirmed working by the user** on real orders moved through those states in Admin. The post-checkout confirmation page (`/order/[id]/confirmed`) deliberately has no tracker (decided not needed).
- **Shared detail-page building blocks**: `StatusTracker` (the step row), `CancelledNotice` (the red banner), `DetailField` (the "Label: value" lines of the info card) and `Help` live in `modules/common` / `modules/order`, and the Materials, Labour and Engineering detail pages all use them — the labour tracker and card were refactored onto them rather than copied. `Help` is the "Need help?" footer: a boxed callout (light background, border, icon, outlined "Contact us" button) rather than plain text, because bare text under the last section read as part of the order itself; it carries a single "Contact us" link (the old Materials block's "Returns & Exchanges" link went to the same `/contact` page and was dropped).
- **Address book: every address used for an order or booking is remembered**: "Manage addresses" (Account → Addresses) is the customer's saved address book — a list of addresses attached to the customer, which both the checkout and the Labour booking form read from to offer "use a saved address". It used to fill only by hand (checkout saved an address solely for a first-time signup with an empty book; Labour never saved one), so the picker usually had nothing to show. Now `placeOrder` (Materials) and `createLabourBooking` (Labour) each call one shared helper, `saveAddressIfNew` (`lib/data/address-book.ts`), after the order/booking succeeds:
  - **Deduplicated**: two addresses are the same place when the street line and pincode match, ignoring case, punctuation and spacing (city and landmark are deliberately excluded — the same house with a different landmark is still the same house).
  - **Defaults are never changed**: a customer's first saved address becomes their default shipping *and* billing address (so the profile's billing address isn't left empty after the first order); every later one is added as a non-default.
  - **Never fails the order**: the whole helper is wrapped so a failed save is only logged — remembering an address is a convenience. It's a no-op for guests and for an address with no street line/pincode.
  - **A fresh read, then a cache refresh**: the duplicate check reads the customer uncached (the cached `retrieveCustomer` could let a duplicate through), and after saving it revalidates the `customers` cache tag — this is why saving lives in the storefront server actions rather than a backend subscriber, which couldn't invalidate the storefront's cached customer record. Account → Addresses shows a new address immediately.
  - **Deliberately not a `"use server"` module** (it's `server-only`): anything exported from a `"use server"` file becomes a function the browser can call directly, and this should only ever run as a step of placing an order/booking. Saved with `country_code: "in"` (otherwise checkout's region filter would hide it) and, for Labour — which has no recipient name — the customer's own name.
  - The old checkout-only mechanism (`saveCartAddressAsDefaultIfNone` and the effect that fired it for a returning customer) was removed rather than left beside this; a first-time customer's address is now saved when they place their order, like everyone else's.
  - **Not done, by choice**: no "Save this address" checkbox (the requirement was to store every address used), and no back-fill of past orders/bookings (there are no real customers yet; it would be a one-off script).
- **A real cross-boundary bug found by live testing, not type-checking**: passing `onConfirmPaid={() => confirmPaymentSubmitted(order.id)}` — a plain closure — from the (Server Component) confirmation page into the (Client Component) `UpiPayment` crashed at runtime ("Event handlers cannot be passed to Client Component props"), even though it type-checked fine. A Client Component can only receive an actual Server Action reference across a server→client prop boundary, not a closure wrapping one — fixed with `.bind(null, booking.id)` instead of an inline arrow, matching the pattern the Materials order-completed-template already used correctly. (The restriction is one-directional: a Client Component calling or passing the same server action to something further down, e.g. from `order-details-template.tsx` which is itself a Client Component, is fine as a plain arrow — only the Server→Client crossing is restricted.)
- **Three usability fixes from live click-through, all server-side-authoritative + client-side-hinted** (same split as every other rule in this document): (1) the per-hour date picker had been reusing the per-day booking's 8:30 AM same-day-cutoff `min` value, which doesn't apply to hour bookings at all — incorrectly blocked "today" after 8:30 AM for an hour booking even when the specific requested time still had a valid 1-hour lead; given its own, simpler `min` (just today). (2) "Number of people" was a controlled numeric input that clamped to a minimum of 1 on every keystroke, making it impossible to clear the field and retype a different digit — switched to a string-backed text input with submit-time validation instead of live clamping, with a red-highlight + inline error shown only after a failed "Continue" attempt. (3) the native `<input type="time">` picker ignores `min`/`max`/`step` once its own scroll-wheel UI opens (confirmed live, not assumed) — replaced with an explicit `<select>` listing exactly the 33 allowed 15-minute-step times within business hours, with the end-time list additionally filtered to only times after whatever start time is currently selected, so an invalid end-before-start combination can't be chosen in the first place (on top of the existing fallback validation + red highlight for the case where no start time is chosen yet).

- **Error messages (cross-cutting fix)**: `medusaError` was written for the older axios-style error shape (`err.response`); the v2 SDK's `FetchError` (what `sdk.client.fetch` throws for any non-2xx) has no `response`, so every server message used to be prefixed "Error setting up the request:". ## 6. Open Items / Risks

- **Manual verification without a captured reference** is an operational risk: admin matches orders to bank statement entries by amount/timing only, which gets ambiguous with multiple same-amount orders close together. Worth revisiting post-launch if verification errors become frequent (e.g. an optional free-text UTR field the customer can voluntarily fill in).
- **Manual/system payment provider + order cancellation has a known upstream rough edge** (medusajs/medusa#14214, open at time of writing) around refund/cancellation workflows for non-gateway providers. Must explicitly test in Phase 4: cancelling an order whose payment is still `pending_authorization`, and cancelling one whose payment is already `captured`. If Medusa's core behavior is unsatisfactory, the fallback is a small custom guard in our own cancel path rather than a full custom payment provider.
- **GST/tax** deferred — default tax-inclusive flat pricing for v1; confirm before launch if a shown tax line is actually required.
- **No RBAC on admin actions for v1** — the payment-verification route (§3.2) authorizes on "any authenticated admin," not a specific role/permission. Medusa v2's RBAC exists but is feature-flagged and has open bugs (permission revocation beyond 20 policies, sidebar not respecting permissions) as of the installed version. Revisit only if the business adds multiple admin staff who need different privilege levels (e.g. a warehouse worker who can fulfill but shouldn't verify payments) — not needed for a single-operator admin team.
- **Medusa API surface must be verified against the exact installed version before each phase that touches it — not against blog posts, older tutorials, or memory.** Installed version, confirmed directly (not assumed): `@medusajs/medusa` and `@medusajs/framework` are both **2.21.0** (`apps/backend/package.json` and `node_modules/@medusajs/*/package.json` agree). This version is pinned for the duration of the build; if it's bumped mid-project, redo the checks below for anything touched afterward. Per-surface, checked against 2.21.0's own docs/type definitions at the point the relevant phase starts, not upfront in bulk:
  - Payment provider base class/interface (`IPaymentProvider` shape, session status enum incl. `pending_authorization`) — Phase 0/4.
  - Auth provider APIs (`AbstractAuthModuleProvider`, `authenticate`/`validateCallback`/`register` signatures) — Phase 2.
  - Workflow APIs (`completeCartWorkflow` composition, `capturePaymentWorkflow`) — Phase 0/4.
  - Admin widget zones (`order.details`, confirmed current for 2.21.0 — the older `.before`/`.after` suffixed zones are deprecated as of 2.17.2 and should not be used) — Phase 4.
  - Admin API authentication (how a custom admin route like `/admin/orders/:id/verify-payment` gets the same session guard as built-in admin routes) — Phase 4.
  - Module registration shape in `medusa-config.ts` (Auth/Payment/Fulfillment/Notification `providers` arrays) — Phase 0/2.
  - Fulfillment APIs (manual provider registration, shipping option/profile creation) — Phase 0.
- **Phone-auth hardening goes beyond Medusa's own reference implementation.** Medusa's official phone-auth tutorial does not implement resend cooldown, max attempts, rate limiting, or phone normalization, and stores the OTP signature with only a bare JWT TTL. §3.1's additions (Redis-backed cooldown/attempts/rate-limits, per-IP middleware, normalization, single-use invalidation) are deliberate hardening on top of that baseline — confirm during Phase 2 implementation that these compose cleanly with the `authenticate`/`validateCallback` lifecycle rather than fighting it (e.g. returning the right error shape from `validateCallback` when a Redis-side guard rejects the attempt before JWT verification even runs).
- **Guest-cart cookie lifetime cut from 7 days to 1 day (security).** Medusa treats knowing a cart's ID as sufficient to read its full contents — including any previously-saved shipping address (name/phone/street) — with no auth check. On a shared/returned-to browser, a long-lived cart cookie left a window where someone could read PII from a session that *was* authenticated when the address was saved but no longer is. Couldn't reliably distinguish "stale cart from days ago" from "guest who just typed a known email mid-checkout" server-side (Medusa auto-links a cart to an existing customer by email match with zero auth, by design — a real, intentional feature elsewhere in this flow), so the fix shrinks the exposure window itself rather than trying to detect staleness. `signout()` already clears both the auth and cart cookies together on explicit logout.
- **Recurring Turbopack dev-server instability**, hit repeatedly during this project's own iteration (not a code issue): `.next` build-cache corruption (`ENOENT` on `_buildManifest.js.tmp.*`) and, separately, a zombie `medusa develop` process quietly holding port 9000 for days while a freshly-started one silently failed to bind. Procedural fix each time — stop stray processes, delete `.next`, restart — never required a code change. Worth a real look before relying on long-running local dev servers for extended sessions.
- **Scope expanded beyond this document's original v1 (Materials-only)**: the user's UI reference design (see docs/PROGRESS.md, "UI Redesign") models two more platforms — Labour & Manpower and Engineering Services — confirmed as real intended scope, not just visual decoration. **Labour & Manpower now has a real backend and booking flow — see §2.10/§3.5/§4.3** (its own architecture pass, as flagged here when this was still placeholder-only). One follow-up from that remains open: `/categories/[handle]` and `/collections/[handle]` still have the pre-redesign layout, visually inconsistent with the restyled `/store`. **Engineering Services now has a quote-request flow too — see §2.11/§3.6/§4.4.** What it deliberately does *not* have is anything beyond lead capture: no quote generation, pricing, or customer-facing status tracking (the business calls back and works the request from Admin).
